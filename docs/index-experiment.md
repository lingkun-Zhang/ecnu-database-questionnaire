# 第一阶段索引执行计划实验

执行日期：2026年10月21日。本实验补充MongoDB设计评分的实测依据，验证现有索引是否匹配实际访问方式；未修改业务查询、集合结构、索引或前端。原始执行计划、逐次耗时、结果摘要、环境与源码摘要均见[完整JSON证据](evidence/index-experiment-20261021.json)。

## 1. 数据、环境与问题

实测环境为Windows 11、Python 3.12.14、PyMongo 4.19.0、MongoDB 6.0.29，本机单节点副本集。自动创建随机命名的独立实验库，使用应用的`init_database`建立相同的strict/error校验器和全部既有索引，没有绕过BSON校验。

| 集合 | 合成数量 | 分布 |
|---|---:|---|
| users | 25 | 20个所有者、5个样例参与者；占位密码哈希，不能登录 |
| surveys | 1,000 | 每个所有者50份；创建时间有并列值，检验_id次排序 |
| survey_versions | 2,000 | 每问卷2个发布版本 |
| responses | 20,000 | 前100份问卷各200份，前100份答卷属于V1、后100份属于V2 |

答案取自已有六份教学样例，经真实领域引擎生成有效路径和答案后批量写入。参与标识、摘要和账号均为合成占位内容；此过程没有执行注册、鉴权、提交事务，不构成两万次正式API提交或并发压测。插入顺序以固定随机种子20261021打乱；答案样式只有六类，不代表生产数据的全部分布。

问题来自现有代码：所有者列表排序、同一次提交查找、固定版本和范围的答卷游标页、完整统计聚合、匿名统计聚合。分页复用`build_response_scope`，统计直接调用`build_stats_pipeline`生成完整`$facet`，没有用简单count替代业务统计。

## 2. 对照方法与正确性

每类查询运行三种方式：

1. `auto`：不指定hint，让MongoDB优化器自行选计划，对应应用的常规查询。
2. `index`：指定已有目标索引，确认该索引确实能执行同一查询。
3. `collection_scan`：指定`hint({$natural:1})`，强制扫描集合形成对照；保留全部索引，不对业务库删索引。方法依据见[MongoDB hint文档](https://www.mongodb.com/docs/manual/reference/method/cursor.hint/)。

每种方式保留一次`explain`的`executionStats`原始结果，并执行一次不计时预热，再交错运行7次实际查询。每轮以固定种子打乱三种方式顺序；客户端计时包括游标创建、网络传输、全部批次和BSON解码，不含之后的摘要或断言计算。缓存未清空，属于预热后的本机读查询；没有记录并发、写入吞吐、冷启动或端到端页面性能。

实际返回结果逐次核对：列表和分页保留顺序；聚合仅将无序分组数组规范排序后比较完整结果摘要。另用独立算术核对列表的次序、游标59到29、幂等回执唯一ID，以及统计份数、人数、评分总和和含0的均值。全部查询的三种方式、全部计时轮次均返回一致结果；不是仅凭耗时认定正确。

`totalDocsExamined`表示检查文档数，`totalKeysExamined`表示检查索引项数；`IXSCAN`是索引扫描，`FETCH`表示仍需读取文档，`SORT`表示阻塞排序。本实验未出现覆盖查询。MongoDB说明`explain`忽略计划缓存，解释中的耗时不等同于稳定运行耗时，因此另测实际查询并只把中位数作为辅助信息。参见[执行计划字段说明](https://www.mongodb.com/docs/manual/reference/explain-results/)。当前官方页面还包含较新版本字段，本实验只解释MongoDB 6.0.29实际返回的字段。

| surveyId+participantKey+submissionKey，limit1 | uq_responses_submission | 1份回执 | 1 / 1 | 3,821 | 无 / 无 |

## 5. 设计结论与取舍

- **列表索引顺序匹配访问方式。** ownerId先等值定位，随后createdAt/_id提供稳定降序，读取30份即可返回首页；全扫还需排序。它不消除现有offset分页在深页的跳过成本，本次仅测首页。
- **幂等唯一索引兼顾一致性和查找。** 三字段等值查询读取1项索引和1份答卷。唯一性是否正确另由既有并发测试证明，不能由本次读取实验代替。
- **版本/序号索引匹配范围和游标。** surveyId、versionId等值前缀后按acceptedSeq范围扫描，读取31份完成30+1的页探测；版本聚合只读取范围内80份，避免检查其他问卷/版本。统计仍须处理这些答案并执行facet，索引没有让聚合计算变成零成本。
- **匿名条件仍是剩余过滤。** 当前索引没有anonymous字段，先取版本/序号范围内80份再筛成40份。这是已观察到的限制；本次数据不足以判定应新增匿名复合索引，暂保留较少的写入维护开销。将来若筛选占比、范围大小或延迟要求发生变化，再对新候选索引进行读写成本实验。
- **收益有数据分布边界。** 当前目标统计只选20,000份中的80份，选择性较高；其他分布和更宽统计范围的收益可能不同。所有索引增加空间和写入维护开销，本次没有测写放大或并发提交热点。

## 6. 复现与数据保护

在已安装依赖、已启动MongoDB的项目根目录执行：

```powershell
& ./.venv/Scripts/python.exe scripts/index_experiment.py --output docs/evidence/index-experiment-rerun.json --repeats 7
```
