# 恢复题目旧版本

记录日期：2026年10月25日。本步从本地提交 `93a54eb` 继续，第一阶段基线 `99b66d1e637fa3b4ecb13719c0230ecb7e958701` 保留。前置能力见[独立题目与不可变版本](phase2-question-versions.md)、[问卷固定使用题目版本](phase2-question-reuse.md)和[题目使用情况查询](phase2-question-usage.md)。

## 范围与恢复语义

任务书明确要求查看题目历史、知道来源并恢复旧版本，但没有指定恢复应覆盖内容、移动指针还是生成新版。结合现有不可变版本和问卷固定引用，本步选择由服务器读取选定版本的完整内容，创建一个带恢复记录的新版本。这个选择属于本项目的设计，不是课程文档或网上资料给定的唯一方案。

例如当前为v3，用户恢复v1，成功后生成v4：v4内容等于v1，当前指针指向v4；v1、v2、v3仍保留。`parentVersionId`继续表示内容来源，因此v4的父版本是v1；恢复前的当前指针另记为v3，不能把二者混为一条线性历史。

本步仅面向私有题所有者，不新增共享、题库管理或前端入口。问卷草稿、发布快照、答卷及其题目来源不自动换版；恢复后如需让问卷使用新恢复版，仍须显式选择该版并按既有规则保存、发布。现有派生接口接收客户端的新内容，不能用它冒充已经实现服务器可信取回旧内容的恢复动作。

## 接口契约

新增 `POST /api/questions/{questionId}/restore`，必须登录并提供 `Idempotency-Key`。请求体只接受两个字段：

| 字段 | 含义与约束 |
|---|---|
| `targetVersionId` | 要恢复内容的已有版本ID，非空字符串，最多160字符，必须属于本题 |
| `expectedCurrentVersionId` | 用户确认时的当前版本ID，非空字符串，最多160字符 |
| `Idempotency-Key`请求头 | 本次恢复的操作标识，长度1—128；重试保留原值和原请求体 |

下例是契约示例，尖括号是实际调用时替换的占位符，不是已经执行的请求记录：

```http
POST /api/questions/<question-id>/restore
Authorization: Bearer <登录凭据>
Idempotency-Key: restore-v1-001
Content-Type: application/json

{"targetVersionId":"<v1-id>","expectedCurrentVersionId":"<v3-id>"}
```

调用方不能提交`content`、`operation`、`parentVersionId`或其他字段来伪造恢复。服务器在写事务中读取所属题目和目标版本，取回完整`kind/title/config`，并创建下一编号的版本。恢复当前版或内容相同的版本也允许：每个成功的新操作标识都会产生一条新版本记录，不以内容相同为由悄悄省略恢复动作。

首次成功返回201；同一成功操作重放返回200及 `Idempotent-Replay: true`，首次响应对应值为false。返回结构沿用版本视图，并在恢复版增加两项元数据。假设上述v1是一道允许0—10整数的评分题，响应结构如下：

```json
{
  "id": "<v4-id>",
  "questionId": "<question-id>",
  "versionNo": 4,
  "parentVersionId": "<v1-id>",
  "content": {
    "kind": "number",
    "title": "本次体验评分",
    "config": {"min": 0, "max": 10, "integerOnly": true}
  },
  "createdAt": "<创建时间>",
  "operation": "restore",
  "previousCurrentVersionId": "<v3-id>"
}
```

ID和时间仍是占位示例；真实内容必须来自所选目标版本。原有未带恢复元数据的版本响应继续使用原字段，不补造操作类型或恢复前指针。恢复版成为历史后仍保留其真实元数据。

| HTTP与错误码 | 含义 |
|---|---|
| 401 `UNAUTHENTICATED` | 未登录或登录凭据失效 |
| 404 `NOT_FOUND` | 题目不存在或当前用户不是所有者 |
| 404 `QUESTION_VERSION_NOT_FOUND` | 在可访问的题目中，目标版本不存在或属于另一题 |
| 409 `QUESTION_VERSION_CONFLICT` | 当前指针与请求预期不符，需刷新后重新决定 |
| 409 `IDEMPOTENCY_CONFLICT` | 已成功的标识被用于不同动作、目标或当前版本预期 |
| 422 `INVALID_REQUEST` | 缺字段、未知字段、类型、长度或请求头不符合要求 |
| 503 `QUESTION_WRITE_OUTCOME_UNKNOWN` | 写入或失败后的恢复查询无法确认结果，保留原操作标识和请求体重试 |

进入写入流程前的数据库访问失败仍沿用全局 `DATABASE_UNAVAILABLE`。状态码及错误语义需由本轮实际API测试核实，不能由示例代替。

## 事务、并发与重试

恢复在同一事务内检查所有者、读取当前题目和目标版本、插入新版，并以预期当前指针和最后版本号为条件更新题目主记录。插入版本与移动指针必须一起成功；冲突或异常整体回滚，不留下孤儿版本或被失败请求占用的版本号。

MongoDB建议将预期当前值放入更新条件，以避免并发覆盖；涉及多文档原子修改时再使用事务，见[官方原子性与事务说明](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)。本步沿用已有事务与比较更新机制，具体行为仍以本机MongoDB 6.0.29的实际测试为准，不将当前在线手册当成本机实测。

请求摘要区分恢复和普通派生，并绑定题目、目标版本及预期当前指针。两种动作共用既有题内请求标识唯一索引，因此不能把派生成功的标识改作恢复，也不能把恢复成功的标识改作派生。初始版本的成功标识同样不可再用于恢复。

成功重放先恢复原结果，即使当前指针后来已前进，也返回当时生成的恢复版；重放本身不能再移动指针、另建版本或返回最新内容。并发恢复、恢复与派生竞争同一预期当前指针时，只允许一个新版本提交。写入结果不明时继续使用原标识，不能换标识重复执行。

## 数据库与旧格式兼容

本步不增加集合或索引，只给`question_versions`增加可选的`operation`和`previousCurrentVersionId`。两字段必须成对出现；出现时`operation`只能为`restore`，且版本号至少为2。已有原字段、版本号/父关系约束及其他集合校验器继续保留。

这些结构约束不能独立保证跨文档归属、历史事实或绝对不可改写。目标版本必须属于本题、恢复前指针必须来自事务实际读取，由服务层建立；应用仍不提供修改或删除旧版本的接口。

旧版本可继续不含两项新字段，`schemaVersion`不变，不回填旧记录。新程序应同时读取旧格式与恢复记录，初始化只安装约束和索引，不能改写旧版本内容、原问卷或答卷。兼容不是仅靠增加一个版本号字段自动获得，参见[MongoDB模式版本说明](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/data-versioning/schema-versioning/)。

新程序读取旧数据可用，不等于旧后端能处理新增恢复元数据。旧后端的严格校验器不认识这些字段，启动时可能覆盖当前约束；程序回退应先停止相关新写入并备份，单独验证版本视图、写入和约束安装，不通过删掉恢复版或改写历史来绕过回退问题。

## 验收计划与实际结果

验收使用随机独立测试库、合成账号和临时测试配置，不读取真实答卷或密钥。测试应核对请求结果与数据库内容，而不只检查HTTP成功。

1. 建立v1、v2、v3，恢复v1生成v4，核对完整内容、来源父版本、恢复前指针及编号；再覆盖四题型、恢复当前版和相同内容。
2. 伪造恢复内容、使用另一题的版本、越权请求或提交非法字段时，检查错误及无部分写入；确认旧版本响应不被补造新字段。
3. 验证同标识重放、换目标或换预期冲突、恢复与派生交叉复用标识，以及当前指针继续前进后的成功重放。
4. 同步放行真实并发恢复及恢复/派生请求，核对唯一成功、版本编号和指针；注入插入后失败，确认事务回滚和原标识可重试。
5. 验证提交后返回丢失的结果恢复、未知写入与恢复查询自身失败的提示。故障注入须说明边界，不将受控服务故障写成真实断网。
6. 恢复前后比较旧版本、问卷草稿、发布快照和既有答卷全文；旧填写凭据继续按原版本提交。使用查询不应凭内容相同就把问卷改关联到恢复版。
7. 直接验证新元数据成对、类型与v1限制，以及旧格式反复初始化；最后运行原发布、填写、统计、题目版本、固定引用及使用查询回归。
