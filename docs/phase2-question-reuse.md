## 本步的范围

独立保存题目之后，问卷还需要证明“这一使用实例来自哪一道题的哪一版”。本步让现有草稿保存接口接收明确的来源映射，服务端核实后与定义一起保存，发布时冻结。两份问卷可以固定使用同一版；题目产生新版后，只有显式换版的问卷变化。

问卷仍保存完整定义，`id/required/defaultTarget/rules`继续属于卷内实例；`kind/title/config`才是独立题目内容。来源映射提供身份依据，不能通过相同题干、内容或局部ID推断。该关系是后续使用查询和跨问卷统计的基础，本步没有实现这两类查询，也没有共享授权、题库分组、选题界面或业务数据迁移。

## 保存接口与最小示例

沿用 `PUT /api/surveys/{surveyId}/draft`，在 `definition/expectedDraftRevision`外增加可选 `questionSources`。没有新增单独的绑定接口。

调用方先用题目所有者身份请求 `GET /api/questions/{questionId}/versions/{versionId}`，取回真实的 `content.kind/title/config`，放入卷内题目；再自行设置实例ID、必答和跳转。下例的题干和配置必须来自该读取结果，尖括号是实际调用时替换的占位符，不能将其视为真实执行记录：

```json
{
  "expectedDraftRevision": 0,
  "definition": {
    "title": "运动调查A",
    "description": "固定使用已保存的题目版本",
    "allowAnonymous": true,
    "entryQuestionId": "exercise_a",
    "questions": [{
      "id": "exercise_a",
      "kind": "number",
      "title": "过去七天运动几次？",
      "required": true,
      "config": {"min": 0, "max": 7, "integerOnly": true},
      "defaultTarget": "END",
      "rules": []
    }]
  },
  "questionSources": [{
    "instanceId": "exercise_a",
    "questionId": "<题目系列ID>",
    "questionVersionId": "<上述读取的版本ID>"
  }]
}
```

服务端逐项验证实例存在、映射不重复、当前用户拥有题目、版本属于该题，以及实例的内容与指定版本经过同一规则规范化后相等。必答与跳转仍接受原问卷规则校验；绑定来源不能绕过发布检查。

| 输入或错误 | 处理 |
|---|---|
| 原草稿没有来源，省略 `questionSources` | 保持第一阶段保存方式 |
| 原草稿已有非空来源，省略该字段 | 409 `QUESTION_SOURCES_REQUIRED`，防止旧客户端静默抹掉关系 |
| 显式 `questionSources: []` | 解除全部引用，保留本次提交的完整题目内容 |
| 显式 `null`、外层格式或字段类型错误 | 422 `INVALID_REQUEST` |
| 悬挂实例、重复映射或内容不符 | 422 `INVALID_QUESTION_SOURCE` |
| 题目不存在或不属于当前用户 | 404 `NOT_FOUND` |
| 已有权限的题目中版本不存在，或版本属于另一题 | 404 `QUESTION_VERSION_NOT_FOUND` |

换版提交的内容必须与所选版本规范化后相等；内容确有变化时，只改映射或只改题干都会被拒绝。不同版本内容相同时，可以只更换映射，成功保存仍递增草稿修订。解绑则需要明确提交更新后的映射，不能靠省略字段表达。来源验证失败时，定义、来源和草稿修订均不得部分写入。

## 数据库、发布与并发

`surveys`增加可选 `draftQuestionSources`，`survey_versions`增加可选 `questionSources`，数组元素均为上述三个ID。只有非空映射才持久化，并仅在所有者的草稿或版本视图中返回；空映射移除该可选字段。旧文档不要求回填，原 `schemaVersion`不变。

两个集合的MongoDB校验器有意扩展可选来源字段的形状；`users/responses`校验器不变。映射是否指向真实私有题、内容是否匹配属于跨集合业务约束，由后端检查。不能把集合校验器描述成已经独立保证全部引用完整性。

定义与来源在同一次 `draftRevision`比较更新中写入；即使只改来源，成功保存也递增修订。并发旧修订继续返回原草稿冲突，避免定义来自一次编辑而来源来自另一次编辑。发布仍使用原修订、当前发布版预期和 `publishKey`；所有来源变动均已进入草稿修订，因此无需另给发布摘要增加一个来源指纹。

发布在原MongoDB事务及其session中重新核实来源，然后深拷贝到发布快照。它读取明确的版本ID，不跟随题目当前指针升级。旧快照保有完整题干、配置与来源；填写和答卷继续使用原发布版本及卷内实例ID。修改题目当前指针不能改变已发布定义或历史答案含义。

## 旧功能与编辑器兼容

原 `definition`、答卷结构和公开填写响应保持原协议；没有来源的旧题继续有效，不自动导入题库或合并身份。旧四集合中的业务文档不因初始化而改写。

现有编辑器只做保存兼容：已有来源时显式携带，并去掉用户已经删除的实例映射；无来源时保留原请求形状。手动修改绑定题的内容仍会被后端拒绝，界面不得静默解绑。历史版本复制总是提交所选版本的 `questionSources ?? []`，防止将当前草稿来源错误贴到历史内容上。

本步没有选题、换版或解绑按钮，绑定链路通过API验证。前端能够继续保存含来源草稿，不等于已经提供完整题库使用体验。

来源错误目前能显示服务端说明，但专用字段定位和编辑后自动清除仍未接入；原定义错误定位继续保留。修改卷内稳定ID按删除旧实例、增加新实例处理，不凭相同内容转移来源。

部署时需要用本版本初始化可选字段校验器，再开始写入引用。不能让第一阶段旧后端同时处理带来源的草稿：它不执行本轮真实性校验，启动时还会安装旧校验器。本步保证旧格式数据在新程序中继续可用，不承诺旧程序可直接处理新增来源。需要回退程序时，应先停止新写入并备份新增元数据，单独安排回退验证，不能删除历史快照来绕过兼容问题。

## 可核算的验收步骤

验收使用隔离MongoDB测试库和合成账号，不读取真实答卷、密钥或个人信息。每组失败请求都应同时检查HTTP错误和数据库无部分变化。

1. 建立数字题v1及问卷A/B，分别用不同实例ID绑定v1并发布。读取所有者快照，核对两卷来源均为v1；公开填写响应应无内部来源映射。
2. 在A旧发布版产生一份有效答卷，记录该版本全文、答卷及统计。创建题目v2，确认A/B草稿与已发布版均未自动变化。
3. 仅把A的内容及映射换为v2，再发布A新版。A新填写使用v2；B及A旧发布版仍为v1。重新读取旧答卷，并在相同asOfSeq或相同答卷集合下比较旧版统计，核对内容、答案及数值一致；旧版新增答卷后，统计应按新增结果变化。
4. 覆盖越权、跨题版本、悬挂/重复实例、伪造内容、`null`、遗漏来源和显式解绑；验证来源规范化与四题型约束，保证无来源旧数据仍能保存、发布和填写。
5. 两个请求竞争同一草稿修订时只允许一个成功；发布与来源校验异常应回滚。历史复制同时覆盖有来源与无来源旧快照，检查来源未错贴，已发布内容未被改写。
