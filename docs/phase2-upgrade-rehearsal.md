# 两版代码的隔离升级与回退演练

记录日期：2026年10月27日。脚本`scripts/phase2_upgrade_rehearsal.py`使用四个随机命名、有精确归属标记的专用测试库。第一阶段代码由本地Git精确导出99b66d1的backend及requirements，当前backend冻结为私有副本；每个阶段在新的Python进程中执行对应版本的真实应用生命周期与ASGI接口，核对导入路径。当前代码当时是44432eb之后未提交的影响查询改动，结果保存了工作树指纹，不虚称它已属于44432eb。

这证明两版真实代码和隔离数据副本上的兼容行为；不是HTTP/TCP部署演练、依赖重新安装、操作系统回滚、真实业务数据迁移或无损降级。两版锁定requirements内容逐字节一致，复用了既有Python环境。没有读取真实.env；所有密钥由本次随机生成并只通过临时进程环境传递。

| 阶段 | 实际动作和结果 |
|---|---|

| 当前程序升级 | 从备份恢复新库后启动当前程序，任何业务写入前四集合全文哈希不变；旧契约仅增加可选来源字段，旧索引保留。旧登录/统计、原提交重放成功；V2已经存在后，V1旧凭据仍按V1提交8成功。随后验证独立题、派生恢复V1→V2→恢复版V3、共享使用、题库固定V1、两个来源卷0/3、独立汇总授权及本人明细隔离。后续新功能写入没有改写此前已保留的legacy记录 |

| 当前程序重新启动 | 在上述混合副本重启当前程序，恢复当前约束，来源和题目三版历史可读；全部业务文档未变。这是恢复当前约束，不是剥除新字段或迁移数据 |
| 恢复升级前备份 | 在第四个专用库恢复升级前BSON、校验器及索引，旧程序初始化后全文与恢复点一致，登录、保存、发布和提交都正常。原升级库仍另行保留且全文未变，直至最后清理 |

旧四集合在升级初始化时未变，不表示演练全程都没有意图内写入：验证旧凭据时新增了一份答卷，后续也显式新增了第二阶段实体。比较分别固定在初始化前后、后续新功能前后，以及混合旧程序尝试写入前后，不混淆这些范围。

## 可以支持的回退方式

直接把旧程序指向第二阶段混合库不属于受支持的回退：旧启动会替换约束，旧代码也不懂来源真实性。实际失败码依入口不同，不能仅凭静态阅读预设都是422；更不能绕过旧初始化、保留新宽松约束来制造“回退通过”。旧程序能够读取部分数据不等于安全管理新数据。

已验证的备份恢复会回到升级前时间点，**不包含此后第二阶段写入**。因此真实切换前需停写、核对备份与恢复点、保留升级后完整副本，再决定是否恢复；本轮没有执行这些生产动作，也没有自动删除来源字段或合并新旧数据。需要保留升级后成果的降级属于另外的数据转换工作，当前未实现。

## 复现和安全边界

专门准备本机27227端口、phase2test副本集后，可在仓库根运行：

```powershell
python scripts/phase2_upgrade_rehearsal.py --mongo-uri 'mongodb://127.0.0.1:27227/?replicaSet=phase2test' --output '.runtime/upgrade-rehearsal-new' --git git
```

脚本拒绝默认业务端口、非回环主机、含账号密码/库名的URI、多主机、错误副本集、任意业务库名、已存在或越出.runtime的输出目录，以及越界Git归档路径。不接受业务库名称，只自行生成四库；清理逐一核对随机库名、私有清单和库内精确标记，归属不符即保留并报错。备份保留BSON类型和索引顺序，原始BSON、合成口令/填写凭据和源码副本仅在忽略的私有输出中。公开结果只有计数、指纹、阶段检查和清理回执。

最终五阶段均完成，四个随机库逐一确认清理。新增25项纯安全测试全部通过，包含URI、数据库名、归属标记、输出路径和归档越界；不是模拟成功存储。完整结果见[演练证据](evidence/phase2-upgrade-rehearsal-20261027.json)，共同环境清理及原项目保护见[收尾记录](evidence/phase2-question-impact-shutdown-20261027.json)。本轮没有自动推送或提交课程平台。
